## 开发与协作失败

1. 最先应该回答的“怎样在本机完成第一次合法构建”没有形成端到端可执行路径，却持续扩建监督体系。首次 guest 预限额、VM 实际配置、跨系统文件身份和最终退出见证仍未选定时，大量局部源码无法接入实际运行。
2. 安全和资源约束需要尊重，但实现路线没有及时与可用平台能力对齐。UNKNOWN 应引导有界证据获取或具体合同决策，不能演变成无限前置条件，也不能假装已经满足。
3. 局部审查确实发现并修复了真实错误，包括时间戳取样顺序、完整间隔、首次故障顺序、出生代际、peer 重放未 STOP、故障后清场被阻断。然而这些收益长期没有转化为运行结果。把“源码零问题”当主要里程碑，使投入与交付脱节。
4. 观察循环的总调用成本发现过晚。原始全量重复采集在单 GPU 下就明显超出 4M 总调用预算。应在写完整监督器前完成整条循环与全部阶段的静态算账，而非随后再重设计协议和调度。
5. 三份权威文档不断追加至数 MB，合同、候选、修订、回执和历史状态混杂，恢复上下文成本巨大，容易把历史 PENDING/UNSTARTED 当现状。保留历史是必要的，但缺少简短、可机械核验的当前决定索引。
6. 用户反复说“继续”，代理仍经常只完成一个 SOURCE 切片；后来虽遵守授权边界，却没有及时交付可供最终决策的完整最小替代方案。工程负责人应对整条路径负责，而不是把未知能力转成用户提供泛泛 owner 或批准的负担。

## adaptive-workflow 的使用教训

RESEARCH、SPIKE FIRST、REDESIGN 等标签没有发挥足够的资源制动作用。应按交付证据执行停损，而非允许“再一个不同切片”绕过停损：同一关键路径连续两个周期没有新增运行证据，就必须冻结扩张并完成可行性/合同决策。新代理、改名和新文档锚点不得重置失败假设次数。

预检必须覆盖整个启动/监督/写入/清场/费用尾部和全部阶段调用向量。每次 spike 只验证一个会改变路线的关键假设，预先定义预算、通过条件和失败后动作。不能把实际运行禁止时的静态审查记为已验证可行。
